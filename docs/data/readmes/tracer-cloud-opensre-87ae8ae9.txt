OpenSRE: The open-source agent for CI/CD reliability

Your CI tells you it broke, but not why or how to fix it. OpenSRE is a CLI agent that reads the failed run, traces the cause and pushes a fix for you to review. Self-hosted, with your own models.

macOS or Linux:

Windows (PowerShell):

& (scriptblock]::Create((irm https://install.opensre.com/install.ps1))) -gh

Then start OpenSRE:

opensre

Why OpenSRE?

AI writes more of the code every month. Someone still has to fix the build.

When CI goes red, it tells you that something failed, not why or how to fix it. Under deadline pressure, teams hit re-run and move on, flaky checks pile up, main stays red, and the real investigation waits for whichever senior engineer has time. OpenSRE is an open-source CI/CD reliability agent that does that investigation for you, built to run on your own infrastructure with your own models:

- Recover from red builds faster: it investigates the moment a run fails, reading logs, testing hypotheses and pushing a fix for you to review
- Fix the cause, not just the rerun: it separates CI-caused failures from code-caused ones, so you fix the right thing
- Know what CI is costing you: failure rate, developer hours lost to unreliable CI, and how long main stays red
- Senior-level context for everyone: every engineer gets the same depth of analysis

SWE-bench1 showed that agents improve fastest with realistic tasks and clear feedback. Pipeline failures are slower, noisier and harder to reproduce than local code tasks, so we hold OpenSRE to the same standard by:

- running real-world end-to-end tests across cloud-backed scenarios (tests/e2e)
- keeping semantic test-catalog naming so e2e vs unit and local vs cloud boundaries stay obvious (tests/README.md)

Start with the CI/CD overview: analyze a repository's CI reliability, fix failing checks on a PR, or set up an agent that keeps CI green.

Quick Start

Contributors: start at main.py for the process entrypoint map.

Run opensre to sign in and get started. The first launch activates the hosted model.

opensre

Webapp contributors can run opensre setup --dev to authenticate through http://localhost:3000.

Interactive shell — with no subcommand, opensre validates your account and starts a REPL (TTY required). You can exit and stay signed out, but the shell only opens for an active account. Describe incidents in plain language, watch the agent work, and use slash commands for session control (/help, /status, /cost, /sessions, /resume, /compact, /new, /exit) and integrations (/integrations list, /integrations verify). Ctrl+C cancels an in-flight turn without losing session state. See interactive shell commands for the full reference.

Headless CLI — run one agent turn non-interactively from a terminal, script, or CI job:

opensre ask "why is checkout-api slow?"

See Headless CLI for stdin prompts, JSON output, and tool approvals.

From Python — drive the agent in-process from your own code (source checkout required):

from surfaces.embedded import start_embedded_session

session = start_embedded_session()
result = session.chat("why is checkout-api slow?")
`answered` is true for any reply text, including a failed model call.
That failure sets accounting_status to "not_run" and stop_reason to "error".
if result.action_result.accounting_status == "completed" and not result.cancelled:
    print(result.primary_response_text)

See Python API for sessions, conversations, and custom output sinks.

For your team's daily loop: embed OpenSRE in the Python services and automations your teammates already use.
Start with the in-repo Python API guide, then use it every day to make incident response repeatable.

Other useful commands:

opensre integrations setup
opensre update
opensre uninstall   # remove opensre and all local data

Deployment

An OpenSRE Cloud managed gateway, an AWS EC2 path, and a general self-hosted option:

- OpenSRE Cloud managed gateway: an organization admin provisions it in the web app; signed-in shell users can check, start, or stop it without handling infrastructure credentials locally.
- Gateway (AMI + systemd): make build-gateway-image then make deploy-gateway — Telegram gateway only, no Docker; the gateway is installed into a server image that new servers start from.
- Self-hosted container (Railway / ECS / Vercel): deploy the repo Dockerfile, select MODE, and set LLM_PROVIDER plus its API key. Use DATABASE_URL only when the gateway needs shared Postgres-backed state, such as Slack Events API replicas.

How OpenSRE Works

When a CI run fails, an alert arrives, or you ask a question, OpenSRE automatically:

1. Fetches the relevant context: failing checks and CI logs, recent commits and deploys, and correlated logs, metrics and traces
2. Masks sensitive identifiers (optional) before external LLM calls
3. Reasons across your connected systems to test hypotheses in a tool-calling loop, separating CI-caused failures from code-caused ones
4. Answers with an evidence-linked response in the conversation
5. Fixes the cause and pushes it to the PR branch for you to review, or suggests next steps and, optionally, executes remediation actions
6. Posts a summary directly to Slack, PagerDuty, or Telegram — no context switching needed

For the current code-level agent architecture after removing the old graph and chain
framework layers, see AGENTS.md.
